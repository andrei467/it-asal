The System Life Cycle

This page covers the five stages of the system life cycle, from analysis to maintenance, the methods used to develop software, and how prototyping helps developers and clients agree what a system should do.

Stages in the system life cycle 16.1

The life cycle of a computer system usually consists of five main stages. Each stage includes a range of tasks, and after the final stage the cycle may repeat with changes or additions.

The five stages

  • Analysis researches the current situation and decides what the new system needs.
  • Design looks at processing, data flow, inputs, outputs and data storage.

Researching a situation

  • Questionnaires: many users, large sample, can be anonymous. Take time to write and give limited information.
  • Interviews: small groups, detailed views, follow-up questions. Slow, and few responses.
  • Observation: see tasks done in person and links between processes. Slow, and people behave differently when watched.
  • Document analysis: study existing forms and data. Never used on its own, because it doesn’t show how documents are used.

Three specifications

  • User requirements: what the client needs the system to do. The client approves it.
  • System: the hardware and software needed. Software is usually chosen first.
  • Design: how the system will look, its data structures and how it will work.

Design tools

  • Data flow diagram (DFD): how data moves around a system. It does not show the order of processes. Levels 0, 1 and 2.
  • System flowchart: data and processes in a whole system. A data dictionary lists field names, data types, sizes and keys.
  • Validation rules: presence, range, type, length and format. Each needs a rule and a helpful error message.
  • Screens and forms: consistent legible fonts, careful colour, no clutter, instructions, enough space. Tick boxes for several answers, drop-downs or option buttons for one.

Development and testing

  • A test plan lists what is tested, the test type, input data, expected result and the actual pass or fail.
  • Valid data is accepted. Invalid data is rejected. Extreme data is accepted but at the very limit.
  • Alpha: developers or specialist testers, near the end of development, controlled. Beta: selected real users try a nearly finished version.
  • White box: developers who know the system test modules in depth. Black box: inputs and outputs only, no knowledge of how it works, checks the requirements are met.

Implementation

  • Parallel: old and new run together. Least risky but duplicates work.
  • Direct changeover: old stops, new starts. Cheap but risky.
  • Phased: parts introduced at different times. Suits large, complex systems.
  • Pilot: one part of the organisation tries it first. Suits systems that need more testing or lots of training.

Documentation and evaluation

  • Requirements and design documentation guide developers and users.
  • Technical documentation helps future maintainers: data dictionary, annotated code, validation rules, test results, backup routines.
  • User documentation: instructions, screenshots, a glossary of terms and a troubleshooting table of problems, causes and solutions.
  • Evaluation checks efficiency, ease of use and whether the system suits its purpose, using the specifications, the user requirements and user feedback.

Maintenance

  • Perfective improves or enhances. Adaptive keeps the system usable when things change. Preventative stops problems arising. Corrective fixes errors and failures.

Methods of software development 16.2

A number of different methods of working can be used to produce software during the development stage.

Five methods

  • Agile: small stages, working software delivered quickly, requirements can change late. Each iteration is a timebox in which part of the software is planned, designed, built and tested. A customer representative (product owner) is available throughout.
  • Iterative: planned rework. Part of each section is built, then customer feedback is used to improve it.
  • Incremental: one part is fully developed, including feedback, before the next. High-priority features come first.
  • RAD: prototyping, strict deadlines and reuse of existing modules. Timeboxes can run in parallel.
  • Waterfall: all requirements gathered at the start and each stage finished before the next.

Strengths and weaknesses

  • Agile and iterative: easy to change and good user fit, but timescales are hard to predict and many iterations are hard to manage.
  • Incremental: users benefit early, but it needs careful planning so the parts integrate.
  • RAD: fast delivery, but little documentation makes maintenance harder.
  • Waterfall: clear structure and timescales, but changes are hard once a stage is complete and user involvement is limited.

Prototyping 16.3

A prototype is an early version of a software solution with limited functionality. It is used to show how a system will look and function.

What a prototype is

  • A prototype is an early version of a software solution with limited functionality.
  • It usually focuses on the user interface, not data structures. The client can try it, give feedback and compare it with the requirements specification.

Types

  • Evolutionary: the first prototype has the core features. It is improved from client feedback until it becomes the product.
  • Incremental: each prototype adds functions to the last. Only clearly understood requirements are built.
  • Throwaway: never part of the final software. Used to explore ideas and fine-tune requirements early, which is cheaper than late changes.
  • Rapid: quickly built working prototypes that are incorporated into the final system.

Strengths and weaknesses

  • Evolutionary: refined over time, but frequent changes need careful management.
  • Incremental: working parts early, but needs careful planning to integrate.
  • Throwaway: quick feedback, but effort is wasted if the ideas are not used.
  • Rapid: quick feedback, but limited functionality and hard to integrate.
